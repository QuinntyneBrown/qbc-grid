# L2 - Detailed Requirements

Terms used throughout:

- **cell** - one column wide by one `rowHeight` tall.
- **tile geometry** - `{ x, y, cols, rows }` in whole cells, origin top-left at `(0, 0)`.
- **occupied** - a cell covered by the geometry of any tile other than the one under
  consideration.
- **valid geometry** - `cols >= 1`, `rows >= 1`, `x >= 0`, `y >= 0`,
  `x + cols <= columns`, and no overlap with an occupied cell.
- **commit** - the grid adopts a proposed geometry. The layout is emitted when the
  adoption changed something, and is not emitted when the proposed geometry is identical
  to the current one.
- **revert** - the grid restores the geometry the tile had before the interaction and
  emits nothing.

---

## L2-001: Column geometry derives from the container
**Traces to:** L1-001

**Requirement:** The grid shall render `columns` equal-width columns that fill the host container content width, deriving column width as `(containerWidth - gap * (columns - 1)) / columns`.

The grid renders `columns` equal-width columns that together fill the content width of
the host container. Column width is `(containerWidth - gap * (columns - 1)) / columns`.
Sub-pixel column widths are permitted; tile edges shall not accumulate rounding drift
across the row.

**Acceptance Criteria:**
1. Given a grid with `columns` of 12 and `gap` of 8 in a container 1544px wide, when the grid renders, then each column is 120px wide.
2. Given that same grid, when a tile spans the last column, then its right edge is flush with the container content box right edge within 1px.
3. Given a grid whose container width changes from 1544px to 1200px, when the resize settles, then every tile is repositioned to the new column width and no tile's stored geometry changes.

---

## L2-002: Tiles are positioned by cell coordinates
**Traces to:** L1-001

**Requirement:** The grid shall place a tile with geometry `{ x, y, cols, rows }` at column `x` and row `y`, spanning `cols` columns and `rows` rows, separated from adjacent tiles by `gap` pixels on both axes.

A tile with geometry `{ x, y, cols, rows }` occupies the rectangle starting at column
`x`, row `y`, spanning `cols` columns and `rows` rows, with `gap` pixels between
adjacent tiles on both axes.

**Acceptance Criteria:**
1. Given `rowHeight` of 60 and `gap` of 8, when a tile has `y` of 2 and `rows` of 3, then its rendered height is 196px and its top offset is 136px.
2. Given two tiles at `x` of 0 and `x` of 3, both `cols` of 3, when the grid renders, then the distance between the first tile's right edge and the second tile's left edge is exactly `gap`.
3. Given a tile with `cols` of 12 in a 12-column grid, when the grid renders, then the tile spans the full container content width.

## L2-003: The grid grows downward to fit its content
**Traces to:** L1-001

**Requirement:** The grid shall size its host to the lowest occupied row and shall impose no maximum row.

The grid's height is the height required by the lowest occupied row. There is no
maximum row.

**Acceptance Criteria:**
1. Given a grid whose lowest tile ends at row 10, when the grid renders, then the grid host height equals 10 rows plus 9 gaps.
2. Given a tile is moved from row 4 to row 40, when the move commits, then the grid host grows to contain row 40 and the page scrolls rather than clipping the tile.
3. Given the only tile in the lowest row is removed, when the layout updates, then the grid host shrinks to the new lowest occupied row.

## L2-004: Grid configuration is coerced to a usable range
**Traces to:** L1-001

**Requirement:** The grid shall coerce `columns` to `max(1, floor(columns))`, `rowHeight` to `max(1, rowHeight)`, and `gap` to `max(0, gap)`, and shall fall back to the documented default for a non-finite value.

`columns`, `rowHeight`, and `gap` are coerced rather than trusted: `columns` becomes
`max(1, floor(columns))`, `rowHeight` becomes `max(1, rowHeight)`, and `gap` becomes
`max(0, gap)`. A non-finite value falls back to the documented default.

**Acceptance Criteria:**
1. Given `columns` is set to 0, when the grid renders, then it renders 1 column and does not throw.
2. Given `columns` is set to 7.6, when the grid renders, then it renders 7 columns.
3. Given `gap` is set to -4 and `rowHeight` to `NaN`, when the grid renders, then `gap` is 0 and `rowHeight` is the default of 60.

## L2-005: Live mode is inert
**Traces to:** L1-002

**Requirement:** In `live` mode the grid shall present no resize handle, no move cursor, and no focusable tile, and shall not change any tile geometry in response to a pointer or keyboard gesture.

In `live` mode the grid presents no resize handle, no move cursor, and no focusable
tile, and no pointer or keyboard gesture changes any tile's geometry.

**Acceptance Criteria:**
1. Given the grid is in `live` mode, when the user presses the pointer on a tile and drags 200px, then no tile moves, no shadow appears, and no layout is emitted.
2. Given the grid is in `live` mode, when a tile is inspected, then no resize handle is present and the tile is not in the tab order.
3. Given the grid is in `live` mode, when the user clicks a tile and presses arrow keys, then no tile geometry changes.

## L2-006: Edit mode presents interaction affordances
**Traces to:** L1-002

**Requirement:** In `edit` mode the grid shall show a move cursor and a resize handle on every unlocked tile and shall place unlocked tiles in the tab order in row-major layout order, and shall show a focus indicator on a tile focused from the keyboard and not on one pressed with the pointer.

In `edit` mode every unlocked tile shows a move cursor over its drag surface, exposes a
resize handle, and is reachable in the tab order in row-major layout order.

**Acceptance Criteria:**
1. Given the grid is switched from `live` to `edit`, when the switch renders, then every unlocked tile shows a resize handle and no tile geometry has changed.
2. Given three unlocked tiles laid out top-left to bottom-right, when the user presses Tab repeatedly from before the grid, then focus visits the tiles in row-major layout order.
3. Given a tile focused from the keyboard in `edit` mode, when it is focused, then a focus indicator drawn from design tokens is visible against the tile background.
4. Given a tile is pressed and released with the pointer in `edit` mode, when the press ends, then the tile carries focus and shows no focus indicator.

---

## L2-007: Leaving edit mode cancels an interaction in flight
**Traces to:** L1-002

**Requirement:** The grid shall revert an interaction in progress when the mode changes away from `edit`.

If the mode changes away from `edit` while a move or resize is in progress, the
interaction reverts.

**Acceptance Criteria:**
1. Given a tile is mid-drag, when the host sets `mode` to `live`, then the tile returns to its original geometry, the overlay is hidden, and no layout is emitted.
2. Given a tile is mid-resize, when the host sets `mode` to `live`, then the tile returns to its original size and no pointer capture remains held.

## L2-008: A locked tile cannot be moved or resized
**Traces to:** L1-003

**Requirement:** The grid shall exclude a tile with `locked` of `true` from every pointer and keyboard interaction while in `edit` mode, and shall present no interaction affordance on it.

A tile with `locked` of `true` is excluded from every interaction path - pointer and
keyboard - while the grid is in `edit` mode. Other tiles are unaffected by its presence
beyond the cells it occupies.

**Acceptance Criteria:**
1. Given the grid is in `edit` mode and a tile is locked, when the user presses the pointer on it and drags 200px, then it does not move and no shadow appears.
2. Given a locked tile in `edit` mode, when it renders, then it exposes no resize handle and is not in the tab order.
3. Given a locked tile and an unlocked tile, when the unlocked tile is dragged over the locked tile's cells, then the shadow is marked invalid.
4. Given a locked tile is unlocked while the grid is in `edit` mode, when the change renders, then the tile becomes draggable and focusable without a reload.

## L2-009: A drag starts only after a movement threshold
**Traces to:** L1-004

**Requirement:** The grid shall begin a drag only after the pointer has travelled 3 px from the press point, shall not suppress interaction with projected content below that threshold, and shall suppress text selection and the browser's native drag for the duration of a gesture and no longer.

A pointer press on an unlocked tile in `edit` mode begins a drag once the pointer has
travelled 3px from the press point. A press and release below that threshold is not a
drag and shall not suppress interaction with projected content.

Above the threshold the grid holds the boundary the other way. Two gestures the browser
performs on its own — selecting text under a moving pointer, and starting a native drag from
an image or a link — run on the same press and would otherwise paint a selection through
every drag. Both are suppressed while a gesture is live, and both return the moment it ends,
because projected content that is meant to be read and copied has every right to be.

**Acceptance Criteria:**
1. Given a tile in `edit` mode, when the user presses and releases without moving, then no drag occurs, no overlay appears, and no layout is emitted.
2. Given a tile in `edit` mode containing a button, when the user clicks that button, then the button's click handler runs.
3. Given a tile in `edit` mode, when the user presses and moves the pointer 4px, then the drag begins and the tile is lifted.
4. Given a tile containing text in `edit` mode, when the user drags that tile 200px across its own content, then no text inside the grid becomes selected.
5. Given a tile containing an image in `edit` mode, when the user drags that tile, then the browser starts no native drag and the grid's drag proceeds.
6. Given a drag has ended, when the user selects text inside a tile, then the selection succeeds.

## L2-010: The dragged tile is lifted and follows the pointer
**Traces to:** L1-004

**Requirement:** While a drag is in progress the grid shall translate the dragged tile with the pointer in pixels and shall paint it above every other tile with the drag elevation, and shall hold that elevation and its compositor promotion for the duration of the gesture and no longer.

While dragging, the tile tracks the pointer continuously in pixels - it is not snapped
to cells - and is painted above every other tile with an elevation shadow.

**Acceptance Criteria:**
1. Given a drag in progress, when the pointer moves 37px right and 12px down, then the tile has translated by exactly that offset from its resting position.
2. Given a drag in progress over another tile, when the two overlap on screen, then the dragged tile is painted above the other tile.
3. Given a drag in progress, when the dragged tile is inspected, then it carries the drag elevation token and resting tiles do not.
4. Given a drag has ended, whether it committed or reverted, when every tile is inspected, then none carries the drag elevation or its compositor promotion.

## L2-011: A shadow marks the landing cell
**Traces to:** L1-004

**Requirement:** While a drag is in progress the grid shall draw a shadow at the cell nearest the dragged tile top-left corner, with `x` clamped to `[0, columns - cols]` and `y` clamped to at least 0.

During a drag a shadow rectangle is drawn at the cell geometry the tile would take on
release. The target is the cell nearest the dragged tile's top-left corner, clamped so
that `x` lies in `[0, columns - cols]` and `y >= 0`.

**Acceptance Criteria:**
1. Given a drag in progress, when the tile's top-left corner is nearest to column 4 row 2, then the shadow is drawn at column 4 row 2 with the tile's current span.
2. Given a 3-column tile in a 12-column grid, when the user drags it far past the right edge, then the shadow stays at `x` of 9.
3. Given a drag in progress, when the user drags above the first row, then the shadow stays at `y` of 0.
4. Given a drag in progress, when the pointer moves within one cell, then the shadow does not move.

## L2-012: An invalid landing cell is signalled and refused
**Traces to:** L1-004

**Requirement:** The grid shall render the shadow in its invalid state when the target geometry overlaps an occupied cell, and shall revert the tile when the pointer is released on an invalid target.

If the shadow geometry overlaps an occupied cell, the shadow renders in its invalid
state and releasing the pointer reverts the tile.

**Acceptance Criteria:**
1. Given a drag whose target cells overlap another tile, when the shadow renders, then it uses the invalid token colour and is visually distinct from the valid state.
2. Given that same drag, when the user releases the pointer, then the tile returns to its original geometry and no layout is emitted.
3. Given a drag that passes over an occupied region and then onto free cells, when the user releases the pointer, then the tile lands on the free cells.

---

## L2-013: A valid drop commits and emits the layout
**Traces to:** L1-004

**Requirement:** The grid shall adopt the shadow geometry when the pointer is released on a valid target, hide the shadow and the overlay, and emit the complete layout exactly once when the adopted geometry differs from the geometry the tile held.

Releasing the pointer over a valid target adopts the shadow geometry and hides the overlay
and shadow. The layout is emitted exactly once when the adopted geometry differs from the
geometry the tile held, and is not emitted when the tile lands on the cells it started
from.

**Acceptance Criteria:**
1. Given a drag to a free region, when the user releases the pointer, then the tile occupies the shadow geometry and the overlay and shadow are removed.
2. Given that same drop, when the layout is emitted, then it is emitted exactly once and contains every tile, with only the dragged tile's `x` and `y` changed.
3. Given a drop that lands a tile on the cells it started from, when the user releases the pointer, then no layout is emitted.

---

## L2-014: A drag can always be abandoned
**Traces to:** L1-004

**Requirement:** The grid shall revert a drag and release pointer capture on `Escape`, on `pointercancel`, and when the window loses focus.

`Escape`, a `pointercancel`, or the window losing focus during a drag reverts the tile
and releases pointer capture.

**Acceptance Criteria:**
1. Given a drag in progress, when the user presses `Escape`, then the tile returns to its original geometry, the overlay is hidden, and no layout is emitted.
2. Given a drag in progress, when the browser dispatches `pointercancel`, then the drag reverts and no pointer capture remains held.
3. Given a drag in progress, when the window loses focus, then the drag reverts.
4. Given a drag that was abandoned, when the user immediately drags the same tile again, then the drag begins normally.

## L2-015: The resize handle is reachable and unambiguous
**Traces to:** L1-005

**Requirement:** The grid shall expose exactly one resize handle per unlocked tile in `edit` mode, at the bottom-right corner, with a hit area of at least 16 px by 16 px, and a press on that handle shall start a resize and shall not start a move.

Each unlocked tile in `edit` mode exposes exactly one resize handle, at its bottom-right
corner, with a hit area of at least 16px by 16px. Pressing the handle starts a resize,
never a move.

**Acceptance Criteria:**
1. Given a tile in `edit` mode, when it renders, then exactly one resize handle is present and it is at the bottom-right corner.
2. Given the resize handle, when its hit area is measured, then it is at least 16px by 16px.
3. Given the user presses the handle and drags, when the interaction begins, then the tile resizes and its `x` and `y` do not change.

## L2-016: Resizing snaps to whole cells with a shadow preview
**Traces to:** L1-005

**Requirement:** While a resize is in progress the grid shall size the tile to the pointer in pixels and shall draw a shadow at the whole-cell span the tile would take on release.

While resizing, the tile's rendered size follows the pointer in pixels and a shadow
marks the whole-cell span it would take on release.

**Acceptance Criteria:**
1. Given a resize in progress, when the pointer has dragged far enough to cover 5 columns, then the shadow spans 5 columns while the tile itself follows the pointer exactly.
2. Given a resize in progress, when the pointer moves within one cell, then the shadow span does not change.
3. Given a resize in progress, when the user releases the pointer over a valid span, then the tile adopts the shadow span and the shadow is removed.

---

## L2-017: Resizing respects declared size limits
**Traces to:** L1-005

**Requirement:** The grid shall clamp every resize to the tile `minCols`, `minRows`, `maxCols`, and `maxRows`, shall default `minCols` and `minRows` to 1, and shall clamp `maxCols` to `columns`.

A tile's `minCols`, `minRows`, `maxCols`, and `maxRows` clamp every resize. Defaults are
`minCols` of 1, `minRows` of 1, and no maximum. `maxCols` is additionally clamped to
`columns`.

**Acceptance Criteria:**
1. Given a tile with `minCols` of 2, when the user drags the handle to make it 1 column wide, then the shadow stays at 2 columns.
2. Given a tile with `maxRows` of 4, when the user drags the handle past 6 rows, then the shadow stays at 4 rows.
3. Given a tile at `x` of 9 in a 12-column grid, when the user drags the handle right without limit, then the shadow stays at 3 columns.
4. Given a tile whose `maxCols` of 20 exceeds a 12-column grid, when the user resizes it to its maximum, then it spans 12 columns.

---

## L2-018: A resize that would overlap is refused
**Traces to:** L1-005

**Requirement:** The grid shall render the resize shadow invalid when the target span overlaps an occupied cell, and shall revert the tile size on release or on `Escape`.

If the resize shadow geometry overlaps an occupied cell, the shadow renders invalid and
releasing the pointer reverts the tile's size.

**Acceptance Criteria:**
1. Given a resize whose target span would cover a neighbouring tile, when the shadow renders, then it uses the invalid token colour.
2. Given that same resize, when the user releases the pointer, then the tile returns to its original span and no layout is emitted.
3. Given a resize in progress, when the user presses `Escape`, then the tile returns to its original span and no layout is emitted.

## L2-019: The overlay is shown only during interaction
**Traces to:** L1-006

**Requirement:** The grid shall show the cell overlay for the duration of a move or resize, shall remove it whether the interaction commits or reverts, shall paint it behind every tile, and shall not let it intercept pointer events.

A cell overlay is rendered when a move or resize starts and removed when it ends,
whether the interaction committed or reverted. The overlay is drawn behind every tile
and never intercepts pointer events.

**Acceptance Criteria:**
1. Given the grid is idle in `edit` mode, when it renders, then no overlay is visible.
2. Given a drag or resize starts, when it begins, then an overlay showing the column and row structure of the whole grid becomes visible behind the tiles.
3. Given an interaction that reverts, when it ends, then the overlay is removed.
4. Given the overlay is visible, when the pointer is over it, then pointer events reach the tile or grid beneath, not the overlay.

## L2-020: A tile can be added at an explicit position
**Traces to:** L1-007

**Requirement:** `addTile` shall insert a tile at the requested geometry after normalization, shall place it at the first free position when the requested cells are occupied, and shall reject an id that is already present.

`addTile` with a complete geometry inserts the tile at that geometry after normalizing
it. If the requested cells are occupied, the grid places the tile at the first free
position instead of overlapping.

**Acceptance Criteria:**
1. Given a grid with free cells at column 6 row 0, when the host adds a tile at that geometry, then the tile renders there and the layout is emitted once.
2. Given the requested cells are already occupied, when the host adds the tile, then the tile is placed at the first free position that fits and no tiles overlap.
3. Given a tile is added with an id that already exists, when the call is made, then the grid rejects the addition and the existing layout is unchanged.

## L2-021: A tile added without a position is placed automatically
**Traces to:** L1-007

**Requirement:** `addTile` without `x` and `y` shall scan row-major from `(0, 0)` for the first position where the span fits, and shall otherwise place the tile at column 0 on the first row below the lowest occupied row.

`addTile` without `x` and `y` scans row-major from `(0, 0)` for the first position where
the tile's span fits without overlapping. If none exists in the occupied rows, the tile
is placed at column 0 on the first row below the lowest occupied row.

**Acceptance Criteria:**
1. Given an empty grid, when a 3-by-2 tile is added without a position, then it is placed at column 0 row 0.
2. Given a grid whose first row is occupied from column 0 to column 5, when a 3-by-1 tile is added without a position, then it is placed at column 6 row 0.
3. Given a grid with no gap large enough in any occupied row, when a tile is added without a position, then it is placed at column 0 on the first row below the lowest occupied row.
4. Given a tile whose `cols` exceeds `columns`, when it is added without a position, then its span is clamped to `columns` before placement.

## L2-022: A tile can be removed by id
**Traces to:** L1-007

**Requirement:** `removeTile` shall remove the tile with the given id, emit the layout, leave every other geometry unchanged, and treat an unknown id as a no-op.

`removeTile` removes the tile with the given id and emits the layout. Removing an
unknown id is a no-op.

**Acceptance Criteria:**
1. Given a grid with three tiles, when the host removes one by id, then two tiles remain and the layout is emitted once.
2. Given a tile is removed, when the layout settles, then no other tile's geometry changed.
3. Given an id that is not present, when the host removes it, then the layout is unchanged and nothing is emitted.
4. Given a tile is mid-drag, when that tile is removed, then the interaction ends cleanly and the overlay is hidden.

## L2-023: The layout is readable and emitted only on change
**Traces to:** L1-008

**Requirement:** The grid shall expose the layout as plain tile records, shall emit it only when a committed interaction, an add, a remove, or a repair changes it, and shall not emit during a drag or resize.

The grid exposes the current layout as an array of plain tile records and emits it when,
and only when, a committed interaction or an add, remove, or normalization changes it.
Nothing is emitted during a drag or resize.

**Acceptance Criteria:**
1. Given a drag across 300px of pointer movement, when the drag is in progress, then no layout is emitted at any point before release.
2. Given a committed move, when the layout is emitted, then it contains one record per tile with `id`, `x`, `y`, `cols`, `rows`, and `locked`.
3. Given the emitted layout, when the host mutates the array or a record it received, then the grid's own state is unaffected.

## L2-024: A layout round-trips without drift
**Traces to:** L1-008

**Requirement:** A layout emitted by the grid shall carry every tile property the host supplied, shall reproduce the same rendered geometry when supplied back to a grid with the same configuration, and shall emit nothing on load when no repair is needed.

A layout emitted by the grid, serialized to JSON and supplied back to a grid with the
same configuration, reproduces the same rendered result and emits nothing on load.

**Acceptance Criteria:**
1. Given a layout emitted after several moves and resizes, when it is serialized and supplied to a fresh grid with the same `columns`, then every tile renders at the same cell geometry.
2. Given that same restore, when the grid initializes, then no layout is emitted, because nothing needed repair.
3. Given a layout restored into a grid with fewer `columns`, when it renders, then each tile is clamped into range and the repaired layout is emitted once.
4. Given tiles carrying `label`, `minCols` and `maxRows`, when the emitted layout is serialized and supplied back, then each tile retains its label and its size limits.

## L2-025: A supplied layout is normalized deterministically
**Traces to:** L1-009

**Requirement:** The grid shall normalize every supplied layout deterministically by dropping records without an id and records with a duplicate id, coercing numbers, clamping spans and coordinates into range, and moving a still-overlapping record down to the first row where it fits.

On every layout input the grid applies, in order: drop records missing an `id` or with a
duplicate `id`, keeping the first; coerce non-finite or non-integer numbers to their
floor and clamp `cols` and `rows` to at least 1; clamp `cols` to `columns`; clamp `x`
into `[0, columns - cols]`; clamp `y` to at least 0; then, walking the records in order,
move any record that still overlaps an earlier one down to the next row where it fits.

**Acceptance Criteria:**
1. Given two records with the same `id`, when the layout is supplied, then only the first is kept.
2. Given a record with `x` of -3, `cols` of 40, and `rows` of 0 in a 12-column grid, when the layout is supplied, then it renders at `x` of 0 with `cols` of 12 and `rows` of 1.
3. Given a record with `y` of `"abc"` or `Infinity`, when the layout is supplied, then it renders at a finite row and the grid does not throw.
4. Given two records that overlap, when the layout is supplied, then the later record is moved down to the first row where it fits and no tiles overlap.
5. Given a layout of 500 records, when it is supplied, then normalization completes and the grid renders without hanging.

## L2-026: Repair is reported once
**Traces to:** L1-009

**Requirement:** The grid shall emit the repaired layout exactly once when normalization changes a supplied layout, and shall emit nothing when it does not.

When normalization changes a supplied layout, the grid emits the repaired layout exactly
once so the host can persist the correction. When nothing changed, nothing is emitted.

**Acceptance Criteria:**
1. Given a layout that needed repair, when the grid renders it, then the repaired layout is emitted exactly once.
2. Given a layout that needed no repair, when the grid renders it, then nothing is emitted.
3. Given the repaired layout is supplied back to the grid, when it renders, then nothing is emitted.

## L2-027: Arrow keys move a focused tile
**Traces to:** L1-010

**Requirement:** With an unlocked tile focused in `edit` mode, each arrow key shall move the tile one cell in that direction, shall refuse a move that leaves the grid or overlaps another tile, and shall retain focus on the tile.

With the grid in `edit` mode and an unlocked tile focused, each arrow key moves the tile
one cell in that direction. A move that would leave the grid or overlap another tile is
refused and the tile does not move.

**Acceptance Criteria:**
1. Given a focused tile at column 3 row 1, when the user presses `ArrowRight`, then the tile moves to column 4 row 1 and the layout is emitted once.
2. Given a focused tile at column 0, when the user presses `ArrowLeft`, then the tile does not move and nothing is emitted.
3. Given a focused tile whose neighbouring cell is occupied, when the user presses the arrow toward it, then the tile does not move and nothing is emitted.
4. Given a focused tile is moved with the keyboard, when the move completes, then the tile retains focus and is within the scrolled viewport.
5. Given a focused tile, when an arrow key is pressed, then the overlay is shown for the duration of the keyboard interaction and hidden when it settles.

## L2-028: Shift and arrow keys resize a focused tile
**Traces to:** L1-010

**Requirement:** With an unlocked tile focused in `edit` mode, `Shift` with a horizontal arrow shall change `cols` by one and `Shift` with a vertical arrow shall change `rows` by one, subject to the size limits and overlap rules of a pointer resize.

With the grid in `edit` mode and an unlocked tile focused, `Shift` with `ArrowRight` or
`ArrowLeft` changes `cols` by one and `Shift` with `ArrowDown` or `ArrowUp` changes
`rows` by one, subject to the same limits and overlap rules as a pointer resize.

**Acceptance Criteria:**
1. Given a focused 2-by-2 tile, when the user presses `Shift+ArrowRight`, then the tile spans 3 columns and the layout is emitted once.
2. Given a focused tile at `minCols`, when the user presses `Shift+ArrowLeft`, then the tile does not shrink and nothing is emitted.
3. Given a focused tile whose growth would overlap a neighbour, when the user presses `Shift+ArrowRight`, then the tile does not grow and nothing is emitted.

## L2-029: Keyboard changes are announced
**Traces to:** L1-010

**Requirement:** The grid shall give every tile a non-empty accessible name and shall announce each committed or refused keyboard move or resize through a polite live region.

Each tile carries an accessible name supplied by the host. Every committed keyboard move
or resize is announced through a polite live region naming the tile and its new position
or size. A refused keyboard action is announced as refused.

**Acceptance Criteria:**
1. Given a tile named "Attitude" moves to column 5 row 2, when the move commits, then a polite live region announces the tile name with its new column and row in one-based terms.
2. Given a tile is resized to 4 by 3, when the resize commits, then the announcement names the new span.
3. Given a keyboard move is refused because the target is occupied, when the key is pressed, then the announcement says the move was blocked and the tile did not move.
4. Given a tile with no host-supplied name, when the grid renders in `edit` mode, then the tile still has a non-empty accessible name derived from its id.

## L2-030: The grid is built for large desktop viewports
**Traces to:** L1-011

**Requirement:** The grid shall keep the same column count and fill its container from 1024 px to 2560 px of container width, shall not emit a layout when the container width changes, and shall not collapse or reflow at any width.

The grid is supported from 1024px to 2560px of container width. Across that range it
fills its container and keeps the same column count. There is no breakpoint behaviour
and no touch support.

**Acceptance Criteria:**
1. Given a 12-column grid, when the container width is 1024px, 1600px, and 2560px in turn, then the grid renders 12 columns at each width and fills the container.
2. Given the container width changes, when the change settles, then tiles are repositioned without emitting a layout.
3. Given the container is narrower than 1024px, when the grid renders, then it still renders 12 columns and simply becomes denser rather than reflowing or collapsing.

## L2-031: Interaction stays within frame budget
**Traces to:** L1-012

**Requirement:** The grid shall apply position and size through compositor-friendly style writes batched to at most one write per animation frame per moved element, shall measure gesture geometry once at gesture start, and shall hold the 95th percentile frame duration at or below 16 ms while one tile among 60 is dragged.

Position and size are applied with compositor-friendly style writes, batched to at most
one write per animation frame per moved element. Geometry needed for a drag is measured
once when the drag starts, not per pointer event.

**Acceptance Criteria:**
1. Given a grid of 60 tiles, each projecting a static content element that neither animates nor updates, when a tile is dragged continuously for two seconds, then the 95th percentile frame duration is at most 16ms.
2. Given a drag in progress, when 20 pointer events are dispatched inside one animation frame, then at most one style write is applied to the dragged tile in that frame.
3. Given a drag in progress, when the pointer moves, then no layout-forcing measurement of the grid or its tiles is performed for that event.
4. Given a grid of 60 tiles, when a tile is dragged, then no tile other than the dragged tile and the shadow has its style mutated.

## L2-032: Tile content is projected, never interpolated as markup
**Traces to:** L1-013

**Requirement:** The grid shall accept tile content through Angular content projection, shall not use `innerHTML`, `outerHTML`, `insertAdjacentHTML`, or any `bypassSecurityTrust` call, and shall preserve the projected view across a move or resize.

Tile content reaches the grid through Angular content projection. The library never uses
`innerHTML`, `outerHTML`, `insertAdjacentHTML`, or any `bypassSecurityTrust` call, and
host-supplied values reach the DOM only through Angular's property and attribute
bindings.

**Acceptance Criteria:**
1. Given a host projects a component into a tile, when the grid renders, then that component instance is created once and is not re-created by a move or resize.
2. Given a tile id or accessible name containing `<img src=x onerror=alert(1)>`, when the grid renders, then the string appears as text and no script executes.
3. Given a tile is moved, when the move commits, then the projected content is not destroyed and its component state is preserved.

## L2-033: The grid ships as a self-contained Angular library
**Traces to:** L1-014

**Requirement:** The grid shall be published from the `components` library as standalone Angular components, shall import nothing from the application or from the `api` and `domain` libraries, shall inject no service defined outside the library, and shall declare Angular as a peer dependency.

The grid is published from the `components` library as standalone Angular components. It
imports nothing from the application, nothing from the `api` or `domain` libraries, and
injects no application service. Angular is a peer dependency.

The packaging obligations above are proved by behaviour rather than by inspection. A test
that read the manifest or scanned the source for injected services would assert the shape
of the codebase, which the repository reserves for the compiler and for review. Each
obligation has a symptom instead: a bundled rather than peer Angular produces a second
runtime and an injector error, and an injected outside service produces a null-injector
failure in an application that never provided it.

**Acceptance Criteria:**
1. Given a bare Angular application that installs the library, supplies its own Angular version, and registers no provider of its own, when it bootstraps and renders a grid with two tiles in `edit` mode, then it starts with no injector error and a tile can be dragged to a new cell.
2. Given that application configures no router, no HTTP client, and no application-level providers, when the grid runs a drag, a resize, and a keyboard move in turn, then every interaction completes and no injector error is raised.

## L2-034: Every visual value comes from a design token
**Traces to:** L1-014

**Requirement:** The grid stylesheets shall read every colour, spacing, radius, elevation, border width, and transition duration as a `var(--qbc-<role>)` custom property owned by the design system.

Colour, spacing, radius, elevation, border width, and transition duration in the grid's
stylesheets are read as `var(--qbc-<role>)` custom properties owned by the design system.
A consumer can restyle the grid by redefining tokens alone.

A literal value is caught by overriding rather than by reading. A hard-coded colour or
duration is exactly the value that fails to move when every token is redefined, so the
override criterion below detects it wherever it hides, and does so without a scan of the
source.

**Acceptance Criteria:**
1. Given a host redefines every token in the `qbc` catalogue to a value distinct from the design system's default, when the grid renders in `edit` mode with a drag in progress, then every colour, radius, border width, elevation, and transition duration the grid paints resolves to the host's value and none retains a library default.
2. Given a host redefines the shadow's valid and invalid colour tokens, when a drag runs, then the shadow renders in the host's colours with no change to the library.
3. Given the design system's token file is not loaded, when the grid renders in `edit` mode with a drag in progress, then every colour, radius, border width, elevation, and transition duration it paints matches the same grid rendered with the token file loaded and no override applied.
