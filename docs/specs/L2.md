# L2 - Detailed Requirements

Terms used throughout:

- **cell** - one column wide by one `rowHeight` tall.
- **tile geometry** - `{ x, y, cols, rows }` in whole cells, origin top-left at `(0, 0)`.
- **occupied** - a cell covered by the geometry of any tile other than the one under
  consideration.
- **valid geometry** - `cols >= 1`, `rows >= 1`, `x >= 0`, `y >= 0`,
  `x + cols <= columns`, and no overlap with an occupied cell.
- **commit** - the grid adopts a proposed geometry. The layout is emitted when the
  adoption changed something, and is not emitted when the proposed geometry is identical
  to the current one.
- **revert** - the grid restores the geometry the tile had before the interaction and
  emits nothing.

---

## L2-001: Column geometry derives from the container
**Traces to:** L1-001

**Requirement:** The grid shall render `columns` equal-width columns that fill the host container content width, deriving column width as `(containerWidth - effectiveGap * (columns - 1)) / columns`, where the effective gap is the configured gap reduced as far as needed to hold the column width above zero.

The grid renders `columns` equal-width columns that together fill the content width of
the host container. Column width is `(containerWidth - effectiveGap * (columns - 1)) / columns`.
Sub-pixel column widths are permitted; tile edges shall not accumulate rounding drift
across the row.

The effective gap is the configured gap in every ordinary configuration and is smaller only
where the configured one leaves no width to divide. Twelve columns and a gap of 100 in a
1024px container consume 1100px in gutters alone, and the unqualified formula returns a
column width of about -6.33px, which is not a width. The gutters are reduced instead, so
the columns stay positive and the grid stays legible at a configuration nothing rejected.

**Acceptance Criteria:**
1. Given a grid with `columns` of 12 and `gap` of 8 in a container 1528px wide, when the grid renders, then each column is 120px wide.
2. Given that same grid, when a tile spans the last column, then its right edge is flush with the container content box right edge within 1px.
3. Given a grid whose container width changes from 1528px to 1200px, when the resize settles, then every tile is repositioned to the new column width and no tile's stored geometry changes.

## L2-002: Tiles are positioned by cell coordinates
**Traces to:** L1-001

**Requirement:** The grid shall place a tile with geometry `{ x, y, cols, rows }` at column `x` and row `y`, spanning `cols` columns and `rows` rows, separated from adjacent tiles by `gap` pixels on both axes.

A tile with geometry `{ x, y, cols, rows }` occupies the rectangle starting at column
`x`, row `y`, spanning `cols` columns and `rows` rows, with `gap` pixels between
adjacent tiles on both axes.

**Acceptance Criteria:**
1. Given `rowHeight` of 60 and `gap` of 8, when a tile has `y` of 2 and `rows` of 3, then its rendered height is 196px and its top offset is 136px.
2. Given two tiles at `x` of 0 and `x` of 3, both `cols` of 3, when the grid renders, then the distance between the first tile's right edge and the second tile's left edge is exactly `gap`.
3. Given a tile with `cols` of 12 in a 12-column grid, when the grid renders, then the tile spans the full container content width.

## L2-003: The grid grows downward to fit its content
**Traces to:** L1-001

**Requirement:** The grid shall size its host to the lowest occupied row and shall impose no maximum row.

The grid's height is the height required by the lowest occupied row. There is no
maximum row: a tile carried downward by an operator is never stopped by a limit of the
grid's.

That is a statement about growth, not about every number a stored record can carry. A
coordinate large enough that the arithmetic stops advancing, or that no browser positions,
is repaired on the way in by [`L2-025`](#l2-025-a-supplied-layout-is-normalized-deterministically)
rather than rendered. The two rules meet without touching: growth has no ceiling, and a
value the numeric and rendering systems cannot represent never becomes a position.

**Acceptance Criteria:**
1. Given a grid whose lowest tile ends at row 10, when the grid renders, then the grid host height equals 10 rows plus 9 gaps.
2. Given a tile is moved from row 4 to row 40, when the move commits, then the grid host grows to contain row 40 and the page scrolls rather than clipping the tile.
3. Given the only tile in the lowest row is removed, when the layout updates, then the grid host shrinks to the new lowest occupied row.

## L2-004: Grid configuration is coerced to a usable range
**Traces to:** L1-001

**Requirement:** The grid shall coerce `columns` to `max(1, floor(columns))`, `rowHeight` to `max(1, rowHeight)`, and `gap` to `max(0, gap)`, shall fall back to the documented defaults of 12 columns, a row height of 60, and a gap of 8 for a non-finite value, and shall reduce the effective gap as far as needed to hold the column width above zero.

`columns`, `rowHeight`, and `gap` are coerced rather than trusted: `columns` becomes
`max(1, floor(columns))`, `rowHeight` becomes `max(1, rowHeight)`, and `gap` becomes
`max(0, gap)`. A non-finite value falls back to its documented default: 12 columns, a row
height of 60, and a gap of 8.

Coercing each value on its own leaves one combination unhandled, because column width
depends on all three and on the container. Where `gap * (columns - 1)` reaches the
container width there is nothing left to divide among the columns. The effective gap is
therefore reduced until each column holds at least one pixel, and where the container is
narrower than its column count the columns divide what there is and the gutters close.

A container of zero width is the same arithmetic and needs no separate rule: every derived
length is zero until the container is measurable, and the observer that reports its width
reports the change. Tiles are repositioned and nothing is emitted, because no tile geometry
moved.

**Acceptance Criteria:**
1. Given `columns` is set to 0, when the grid renders, then it renders 1 column and does not throw.
2. Given `columns` is set to 7.6, when the grid renders, then it renders 7 columns.
3. Given `gap` is set to -4 and `rowHeight` to `NaN`, when the grid renders, then `gap` is 0 and `rowHeight` is the default of 60.
4. Given `columns` is set to `NaN` and `gap` to `Infinity`, when the grid renders, then it renders 12 columns with a gap of 8.
5. Given a 12-column grid with `gap` of 100 in a container 1024px wide, when the grid renders, then every column width is greater than zero and the last column's right edge stays within the container content box.
6. Given a container of zero width holding a grid, when the container becomes measurable at 1600px, then the tiles are repositioned to the new column width and nothing is emitted.

## L2-005: Live mode is inert
**Traces to:** L1-002

**Requirement:** In `live` mode the grid shall present no resize handle, no move cursor, and no focusable tile, and shall not change any tile geometry in response to a pointer or keyboard gesture.

In `live` mode the grid presents no resize handle, no move cursor, and no focusable
tile, and no pointer or keyboard gesture changes any tile's geometry.

**Acceptance Criteria:**
1. Given the grid is in `live` mode, when the user presses the pointer on a tile and drags 200px, then no tile moves, no shadow appears, and no layout is emitted.
2. Given the grid is in `live` mode, when a tile is inspected, then no resize handle is present and the tile is not in the tab order.
3. Given the grid is in `live` mode, when the user clicks a tile and presses arrow keys, then no tile geometry changes.

## L2-006: Edit mode presents interaction affordances
**Traces to:** L1-002

**Requirement:** In `edit` mode the grid shall show a move cursor and a resize handle on every unlocked tile and shall place unlocked tiles in the tab order in row-major layout order, and shall show a focus indicator on a tile focused from the keyboard and not on one pressed with the pointer.

In `edit` mode every unlocked tile shows a move cursor over its drag surface, exposes a
resize handle, and is reachable in the tab order in row-major layout order.

**Acceptance Criteria:**
1. Given the grid is switched from `live` to `edit`, when the switch renders, then every unlocked tile shows a resize handle and no tile geometry has changed.
2. Given three unlocked tiles supplied in an order that is not their row-major order, when the user presses Tab repeatedly from before the grid, then focus visits them in row-major layout order rather than in the order they were supplied.
3. Given a tile focused from the keyboard in `edit` mode, when it is focused, then a focus indicator drawn from design tokens is visible against the tile background.
4. Given a tile is pressed and released with the pointer in `edit` mode, when the press ends, then the tile carries focus and shows no focus indicator.

## L2-007: A host change cancels an interaction in flight
**Traces to:** L1-002

**Requirement:** The grid shall revert an interaction in progress when the mode changes away from `edit`, when a different layout is supplied, when `columns`, `rowHeight`, or `gap` changes, or when the tile under interaction is locked, shall adopt the incoming state in each case, and shall refuse a keyboard command while a pointer interaction is in progress.

If the mode changes away from `edit` while a move or resize is in progress, the
interaction reverts.

A mode change is one of a set rather than a case on its own. A gesture holds a cell it
proposes and a measurement of the grid it proposed against, and a host is free to replace
the layout, change the column count, or lock the tile being dragged while the pointer is
still down. Each of those makes the proposal describe a grid that no longer exists, and
committing it afterwards would overwrite the state the host has just supplied with a drop
computed against the state it replaced. So the gesture reverts and the incoming state is
adopted whole; the operator loses a drag they can repeat, rather than the host losing an
update it cannot.

A change of container width is the exception, and it is one because nothing the host
believes has changed. The layout is the same layout and the columns are the same columns;
only the pixels beneath them differ. `L2-030` requires the gesture to continue against the
new column width, which means the cached geometry and the offset between the pointer and
the tile's corner are both rebased so the lifted tile stays under the cursor.

A keyboard command during a pointer gesture is refused for the same reason, from the other
direction: two owners proposing geometry for one tile have no defined order, and the
pointer is the one the operator is holding.

**Acceptance Criteria:**
1. Given a tile is mid-drag, when the host sets `mode` to `live`, then the tile returns to its original geometry, the overlay is hidden, and no layout is emitted.
2. Given a tile is mid-resize, when the host sets `mode` to `live`, then the tile returns to its original size and no pointer capture remains held.
3. Given a tile is mid-drag, when the host supplies a different layout, then the drag reverts, the supplied layout is rendered, and no layout is emitted.
4. Given a tile is mid-drag, when the host changes `columns`, then the drag reverts and the grid renders the new column count.
5. Given a tile is mid-drag, when the host locks that tile, then the drag reverts and no layout is emitted.
6. Given a tile is mid-drag, when an arrow key is pressed, then no tile geometry changes from the keyboard.

**Traces to:** L1-003

2. Given a locked tile in `edit` mode, when it renders, then it exposes no resize handle and is not in the tab order.
3. Given a locked tile and an unlocked tile, when the unlocked tile is dragged over the locked tile's cells, then the shadow is marked invalid.
4. Given a locked tile is unlocked while the grid is in `edit` mode, when the change renders, then the tile becomes draggable and focusable without a reload.

## L2-009: A drag starts only after a movement threshold
**Traces to:** L1-004

**Requirement:** The grid shall begin a drag only after the primary button has travelled 3 px from the press point, shall ignore a press that originates on an interactive or editable descendant of a tile, shall hold a press that has not reached the threshold as a pending state it discards on release wherever that release occurs, shall not suppress interaction with projected content below that threshold, and shall suppress text selection and the browser's native drag for the duration of a gesture and no longer.

A pointer press on an unlocked tile in `edit` mode begins a drag once the pointer has
travelled 3px from the press point. A press and release below that threshold is not a
drag and shall not suppress interaction with projected content.

Above the threshold the grid holds the boundary the other way. Two gestures the browser
performs on its own — selecting text under a moving pointer, and starting a native drag from
an image or a link — run on the same press and would otherwise paint a selection through
every drag. Both are suppressed while a gesture is live, and both return the moment it ends.

Which press belongs to the grid is settled by where it lands. A press that originates on an
interactive or editable descendant of a tile — a control, a field, an editable region — is
the descendant's, and the grid neither starts a drag from it nor suppresses it. Every other
press on the tile surface is the grid's. Restoring selection when a gesture ends does not on
its own return selection to the tile surface in `edit` mode: the next attempt to select is
a press and a drag across the same surface, it crosses the same 3 px, and it begins another
drag. The surface is a drag surface while the grid is in `edit` mode, and text on it is read
in `live` mode or inside a descendant that owns its own input.

**Acceptance Criteria:**
1. Given a tile in `edit` mode, when the user presses and releases without moving, then no drag occurs, no overlay appears, and no layout is emitted.
2. Given a tile in `edit` mode containing a button, when the user clicks that button, then the button's click handler runs.
3. Given a tile in `edit` mode, when the user presses and moves the pointer 4px, then the drag begins and the tile is lifted.
4. Given a tile containing text in `edit` mode, when the user drags that tile 200px across its own content, then no text inside the grid becomes selected.
5. Given a tile containing an image in `edit` mode, when the user drags that tile, then the browser starts no native drag and the grid's drag proceeds.
6. Given the grid is in `live` mode, when the user drags across text inside a tile, then the text is selected and no tile moves.
7. Given a tile in `edit` mode containing a text input, when the user drags across the text in that input, then the text is selected and the tile does not move.
8. Given a press 1px inside a tile's edge, when the pointer crosses the threshold outside that tile, then the drag begins.
9. Given a press released outside the tile before the threshold was crossed, when the pointer later moves with no button held, then no drag begins.
10. Given a press with a button other than the primary one, when the pointer moves past the threshold, then no drag begins.

## L2-010: The dragged tile is lifted and follows the pointer
**Traces to:** L1-004

**Requirement:** While a drag is in progress the grid shall translate the dragged tile with the pointer in pixels and shall paint it above every other tile with the drag elevation, and shall hold that elevation and its compositor promotion for the duration of the gesture and no longer.

While dragging, the tile tracks the pointer continuously in pixels - it is not snapped
to cells - and is painted above every other tile with an elevation shadow.

**Acceptance Criteria:**
1. Given a drag in progress, when the pointer moves 37px right and 12px down, then the tile has translated by exactly that offset from its resting position.
2. Given a drag in progress over another tile, when the two overlap on screen, then the dragged tile is painted above the other tile.
3. Given a drag in progress, when the dragged tile is inspected, then it carries the drag elevation token and resting tiles do not.
4. Given a drag has ended, whether it committed or reverted, when every tile is inspected, then none carries the drag elevation or its compositor promotion.

## L2-011: A shadow marks the landing cell
**Traces to:** L1-004

**Requirement:** While a drag is in progress the grid shall draw a shadow at the cell nearest the dragged tile top-left corner, with `x` clamped to `[0, columns - cols]` and `y` clamped to at least 0.

During a drag a shadow rectangle is drawn at the cell geometry the tile would take on
release. The target is the cell nearest the dragged tile's top-left corner, clamped so
that `x` lies in `[0, columns - cols]` and `y >= 0`.

**Acceptance Criteria:**
1. Given a drag in progress, when the tile's top-left corner is nearest to column 4 row 2, then the shadow is drawn at column 4 row 2 with the tile's current span.
2. Given a 3-column tile in a 12-column grid, when the user drags it far past the right edge, then the shadow stays at `x` of 9.
3. Given a drag in progress, when the user drags above the first row, then the shadow stays at `y` of 0.
4. Given a drag in progress, when the pointer moves within one cell, then the shadow does not move.

## L2-013: A valid drop commits and emits the layout
**Traces to:** L1-004

**Requirement:** The grid shall adopt the shadow geometry when the pointer is released on a valid target, hide the shadow and the overlay, release pointer capture, and emit the complete layout exactly once when the adopted geometry differs from the geometry the tile held.

Releasing the pointer over a valid target adopts the shadow geometry and hides the overlay

## L2-014: A drag can always be abandoned
**Traces to:** L1-004

**Requirement:** The grid shall revert a drag and release pointer capture on `Escape`, on `pointercancel`, on unexpected loss of pointer capture, and when the window loses focus, shall remove the shadow and the overlay on each of them, and shall treat the capture loss that follows its own release as complete rather than as a cancellation.

`Escape`, a `pointercancel`, the loss of pointer capture, or the window losing focus
during a drag reverts the tile and releases pointer capture.

Capture loss has an event of its own and is not the same as a cancellation: the browser
raises it when the captured element is removed from the document, and it also raises it
immediately after every release the grid performs itself. The first is a gesture that
ended without an outcome and reverts. The second is the ordinary end of a committed drag
and changes nothing, so the path that handles it is idempotent rather than a second
cancellation running over a finished gesture.

**Acceptance Criteria:**
1. Given a drag in progress, when the user presses `Escape`, then the tile returns to its original geometry, the overlay and the shadow are removed, and no layout is emitted.
2. Given a drag in progress, when the browser dispatches `pointercancel`, then the drag reverts, the shadow is removed, and no pointer capture remains held.
3. Given a drag in progress, when the window loses focus, then the drag reverts and the shadow is removed.
4. Given a drag that was abandoned, when the user immediately drags the same tile again, then the drag begins normally.
5. Given a drag in progress, when the browser dispatches `lostpointercapture` without a release, then the drag reverts, the shadow is removed, and no layout is emitted.
6. Given a drag released on a free target, when `lostpointercapture` follows that release, then the committed geometry is unchanged and nothing further is emitted.

## L2-021: A tile added without a position is placed automatically
**Traces to:** L1-007

**Requirement:** `addTile` without `x` and `y` shall scan row-major from `(0, 0)` for the first position where the span fits, shall otherwise place the tile at column 0 on the first row below the lowest occupied row, and shall bound its search by the records present rather than by the coordinates they carry.

`addTile` without `x` and `y` scans row-major from `(0, 0)` for the first position where
the tile's span fits without overlapping. If none exists in the occupied rows, the tile
is placed at column 0 on the first row below the lowest occupied row.

The scan advances past a blocker rather than through it. A candidate that intersects an
occupant cannot fit at any row before that occupant ends, so the search resumes at the
occupant's bottom row and tests no row in between. The result is the same first fit; the
work follows the number of records rather than the size of the coordinates. Stopping below
the lowest occupied row bounds the rows, and a single tile declaring a billion of them
makes that bound worthless on its own.

**Acceptance Criteria:**
1. Given an empty grid, when a 3-by-2 tile is added without a position, then it is placed at column 0 row 0.
2. Given a grid whose first row is occupied from column 0 to column 5, when a 3-by-1 tile is added without a position, then it is placed at column 6 row 0.
3. Given a grid with no gap large enough in any occupied row, when a tile is added without a position, then it is placed at column 0 on the first row below the lowest occupied row.
4. Given a tile whose `cols` exceeds `columns`, when it is added without a position, then its span is clamped to `columns` before placement.
5. Given a grid whose first row holds a full-width tile with `rows` of one billion, when a tile is added without a position, then it is placed on the first row below that tile and the addition completes within the suite's ordinary timeout.

## L2-023: The layout is readable and emitted only on change
**Traces to:** L1-008

**Requirement:** The grid shall expose the layout as plain tile records, shall emit it only when a committed interaction, an add, a remove, or a repair changes it, and shall not emit during a drag or resize.

The grid exposes the current layout as an array of plain tile records and emits it when,
and only when, a committed interaction or an add, remove, or normalization changes it.
Nothing is emitted during a drag or resize.

**Acceptance Criteria:**
1. Given a drag across 300px of pointer movement, when the drag is in progress, then no layout is emitted at any point before release.
2. Given a committed move, when the layout is emitted, then it contains one record per tile with `id`, `x`, `y`, `cols`, `rows`, and `locked`.

## L2-025: A supplied layout is normalized deterministically
**Traces to:** L1-009

**Requirement:** The grid shall normalize every supplied layout deterministically by treating a supplied value that is not an array as an empty layout, dropping entries that are not records and records without a usable id or with a duplicate id, coercing numbers, size limits, and optional fields, clamping spans and coordinates into range and into the rows it can represent, and moving a still-overlapping record down to the first row where it fits, bounding its search by the records present rather than by the coordinates they carry.

On every layout input the grid applies, in order: drop records missing an `id` or with a
duplicate `id`, keeping the first; coerce non-finite or non-integer numbers to their
floor and clamp `cols` and `rows` to at least 1; clamp `cols` to `columns`; clamp `x`
into `[0, columns - cols]`; clamp `y` into `[0, maxRow]` and `rows` into `[1, maxRow]`;
then, walking the records in order, move any record that still overlaps an earlier one down
to the next row where it fits.

A record reaches that sequence only after the envelope around it has been decided, and the
envelope is part of the contract rather than a detail beneath it. A supplied value that is
not an array is an empty layout. An entry that is not an object is dropped. An `id` is
usable when it is a string with a non-space character in it, so an empty or blank id is
dropped alongside a missing one rather than producing a tile no announcement can name.
`locked` is read as a boolean and any other value is false; `label` is kept when it is a
string and dropped otherwise; each of `minCols`, `minRows`, `maxCols`, and `maxRows` is
kept when it floors to a finite integer of at least 1 and dropped otherwise. A maximum
below its own minimum is raised to that minimum, so `minCols` of 8 with `maxCols` of 2
resolves to 8 and 8 rather than to a tile that can be neither grown nor shrunk.

`maxRow` is 1048576, and it is a bound on what a stored record may claim rather than on how
far a grid may grow. Two things fail above it. Integer arithmetic stops advancing: at
2^53 the expression `y + 1` equals `y`, so a loop looking for the next free row never finds
one. And no target browser positions an element that far down, so a row that survived the
arithmetic would still not render. A million rows is past any dashboard and inside both
limits.

The downward search skips rather than steps. A candidate row that intersects an occupant
cannot fit at any row before that occupant ends, so the search resumes at that occupant's
bottom row. Five hundred records settle in work proportional to the records; a single
record declaring a billion rows costs one comparison rather than a billion.

**Acceptance Criteria:**
1. Given two records with the same `id`, when the layout is supplied, then only the first is kept.
2. Given a record with `x` of -3, `cols` of 40, and `rows` of 0 in a 12-column grid, when the layout is supplied, then it renders at `x` of 0 with `cols` of 12 and `rows` of 1.
3. Given a record with `y` of `"abc"` or `Infinity`, when the layout is supplied, then it renders at a finite row and the grid does not throw.
4. Given two records that overlap, when the layout is supplied, then the later record is moved down to the first row where it fits and no tiles overlap.
5. Given a layout of 500 records, when it is supplied, then normalization completes and the grid renders without hanging.
6. Given a record whose `y` is `2 ** 53`, when the layout is supplied, then it renders at a row the grid represents and normalization completes.
7. Given a full-width record with `rows` of one billion at row 0 and a later record that overlaps it, when the layout is supplied, then the later record is moved to the first row below the blocker and normalization completes within the suite's ordinary timeout.
8. Given a stored layout that is `null`, a number, or an array holding `null` and a usable record, when it is supplied, then the grid renders the records it can use and does not throw.
9. Given a record with `minCols` of 8 and `maxCols` of 2, when the layout is supplied, then the repaired record carries limits that agree, and supplying the repaired layout again changes nothing.

## L2-027: Arrow keys move a focused tile
**Traces to:** L1-010

**Requirement:** With an unlocked tile focused in `edit` mode, each arrow key shall move the tile one cell in that direction, `Control` with an arrow shall move it to the nearest position in that direction where it fits, each shall refuse a move that leaves the grid or finds no free position, each shall retain focus on the tile, and the grid shall consume a key only while the tile surface itself holds focus.

With the grid in `edit` mode and an unlocked tile focused, each arrow key moves the tile
one cell in that direction. A move that would leave the grid or overlap another tile is
refused and the tile does not move.

`Control` with an arrow moves the tile to the nearest position in that direction where it
fits, passing over whatever stands between. A single cell separates the two commands only
when the neighbouring cell is free, and an obstruction is what tells them apart: the
unmodified arrow stops at it, and `Control` steps beyond it to the first position that
holds the tile. Without that second command a full-width locked row divides the grid in
two for a keyboard operator while a pointer crosses it in one drag, and the parity
`L1-010` states would hold only where nothing was in the way. The downward search is
bounded by the lowest occupied row, below which every row is free.

**Acceptance Criteria:**
1. Given a focused tile at column 3 row 1, when the user presses `ArrowRight`, then the tile moves to column 4 row 1 and the layout is emitted once.
2. Given a focused tile at column 0, when the user presses `ArrowLeft`, then the tile does not move and nothing is emitted.
3. Given a focused tile whose neighbouring cell is occupied, when the user presses the arrow toward it, then the tile does not move and nothing is emitted.
4. Given a focused tile is moved with the keyboard far enough to change its place in the row-major order, when the move completes, then the tile retains focus and is within the scrolled viewport.
5. Given a focused tile, when an arrow key is pressed, then the overlay is shown for the duration of the keyboard interaction and hidden when it settles.
6. Given a focused 1-by-1 tile at column 0 row 0 and a locked tile spanning every column at row 1, when the user presses `Control+ArrowDown`, then the tile moves to column 0 row 2, the locked tile keeps its geometry, and the layout is emitted once.
7. Given a focused tile whose neighbouring cell below is free, when the user presses `Control+ArrowDown`, then the tile moves one cell rather than past the free cell.
8. Given a focused tile at column 0, when the user presses `Control+ArrowLeft`, then the tile does not move and nothing is emitted.
9. Given a tile in `edit` mode containing a focused text input, when the user presses `ArrowRight`, then the caret moves within the input, the tile does not move, and nothing is emitted.

## L2-031: Interaction stays within frame budget
**Traces to:** L1-012

**Requirement:** The grid shall apply position and size through compositor-friendly style writes batched to at most one style-attribute mutation per animation frame per moved element, shall measure gesture geometry once at gesture start and again only when the container width changes, shall resolve the final pointer sample on release and discard any pending preview write, and shall hold the 95th percentile of per-frame main-thread work at or below 16 ms while one tile among 60 is dragged.

Position and size are applied with compositor-friendly style writes, batched to at most
one write per animation frame per moved element. Geometry needed for a drag is measured
once when the drag starts, not per pointer event, and again only when the container width
changes, which `L2-030` requires.

A write is one mutation of an element's style attribute. Setting the two drag offsets in a
single scheduled callback is one write, because one render transaction reaches the browser;
counting each custom property separately would make the budget a statement about the number
of properties rather than about the work the browser does.

The measured quantity is the main-thread work attributable to the gesture within a frame —
script, style, layout, and paint — rather than the interval between frames. An unblocked
60Hz stream presents every `1000 / 60` ms, which is 16.667 ms, so a budget of 16 ms read as
an inter-frame interval fails a run in which nothing was dropped at all. Work is what the
design controls and what a slow frame is caused by.

Release resolves the last pointer sample it received, discards any preview write still
scheduled, adopts the result, and clears the preview styles in that order. A release
arriving before a scheduled frame would otherwise commit the position of the frame before
it, and a cancellation leaving a callback queued would repaint a preview belonging to a
gesture that has ended.

**Acceptance Criteria:**
1. Given a grid of 60 tiles on the reference runner, each projecting a static content element that neither animates nor updates, when a tile is dragged continuously for two seconds, then the 95th percentile of per-frame main-thread work is at most 16ms.
2. Given a drag in progress, when 20 pointer events are dispatched inside one animation frame, then at most one style write is applied to the dragged tile in that frame.
3. Given a drag in progress, when the pointer moves, then no layout-forcing measurement of the grid or its tiles is performed for that event.
4. Given a grid of 60 tiles, when a tile is dragged, then no tile other than the dragged tile and the shadow has its style mutated.
5. Given a drag whose pointer moves and is released before the next animation frame, when the drop commits, then the committed geometry is the one the final pointer position names.
6. Given a drag cancelled while a frame is still scheduled, when that frame runs, then no preview is painted.

## L2-034: Every visual value comes from a design token
**Traces to:** L1-014

**Requirement:** The grid stylesheets shall read every colour, spacing, radius, elevation, border width, and transition duration as a `var(--qbc-<role>)` custom property owned by the design system, and shall resolve both duration tokens to zero where the operator has asked for reduced motion.

Colour, spacing, radius, elevation, border width, and transition duration in the grid's
stylesheets are read as `var(--qbc-<role>)` custom properties owned by the design system.
A consumer can restyle the grid by redefining tokens alone.

A literal value is caught by overriding rather than by reading. A hard-coded colour or
duration is exactly the value that fails to move when every token is redefined, so the
override criterion below detects it wherever it hides, and does so without a scan of the
source.

**Acceptance Criteria:**
1. Given a host redefines every token in the `qbc` catalogue to a value distinct from the design system's default, when the grid renders in `edit` mode with a drag in progress, then every colour, radius, border width, elevation, and transition duration the grid paints resolves to the host's value and none retains a library default.
2. Given a host redefines the shadow's valid and invalid colour tokens, when a drag runs, then the shadow renders in the host's colours with no change to the library.
3. Given an operator whose system asks for reduced motion, when a refused drop settles and the overlay is dismissed, then the tile arrives and the overlay clears without an animated transition, and a held arrow key still reveals the overlay for the run of commands and still produces one announcement rather than one for each.
4. Given the design system's token file is not loaded, when the grid renders in `edit` mode with a drag in progress, then every colour, radius, border width, elevation, and transition duration it paints matches the same grid rendered with the token file loaded and no override applied.
